# Living World Simulator — 코어 경화 + 종족 기준 관계 기반 구현 프롬프트

## 역할과 작업 위치

당신은 Godot 4.6/GDScript 기반 헤드리스 시뮬레이션 코어를 경화하는 구현 담당자다.

- 작업 프로젝트: `/mnt/d/STARTU/living-world-sim`
- 다른 프로젝트(`PROJ_G`, `slime-automation` 등)는 절대 수정하지 않는다.
- 기존 코드를 먼저 모두 읽고, 현재 공개 API와 테스트를 파악한 뒤 수정한다.
- 그래픽, 씬, 에셋은 만들지 않는다.
- 구현 후 모든 테스트와 데모를 직접 실행하고 결과를 보고한다.

## 최종 목표

현재의 “단일 명령 + 환경 틱” 프로토타입을 다음 시스템을 안전하게 올릴 수 있는 결정론적 기반으로 개선한다.

1. 명령 검증과 턴 소비 계약
2. 불·물·젖음·전기의 일관된 단일 반응 단계
3. 환경 사건의 끊기지 않는 인과관계
4. 피해·사망 처리의 단일 진입점
5. 저장/복원 후에도 이어지는 결정론
6. 런타임 오류를 성공으로 오인하지 않는 테스트 계약
7. **종족 간 기준 관계가 개인 관계보다 우선하는 관계 시스템 기반**

관계 설계의 필수 철학은 다음과 같다.

> 인간이 적대적인 고블린 한 명을 한 번 구조했다고 해서 그 고블린이 즉시 인간을 신뢰해서는 안 된다. 구조는 우선 감사와 작은 개인 보정으로 남고, 강한 종족·세력 기준선은 반복된 경험이나 명시적인 화해/유대 상태가 생기기 전까지 지배적이어야 한다.

## A. 명령과 턴 코어 경화

### A1. 명시적인 실행 결과

`Simulator.step()`의 결과에 최소한 다음을 표현한다.

```text
accepted: bool
consumes_turn: bool
reason: String
events: Array
```

전용 `SimStepResult` 모델을 권장하지만 같은 계약을 명확히 만족하는 다른 작은 구조도 허용한다. 기존 테스트와 데모는 새 API에 맞게 모두 갱신한다.

### A2. 검증 규칙

- `null` 또는 잘못된 명령 객체 거부
- 알려지지 않은 명령 타입 거부
- 지도 범위 밖 위치 거부
- 원소 위력은 `1..100`만 허용하고 음수, 0, 101 이상 거부
- `actor_id == -1`은 테스트·환경 설정용 시스템 명령으로 허용
- `actor_id >= 0`이면 개체가 존재하고 살아 있어야 함
- 거부된 입력은 턴, 환경, RNG 상태를 절대 진행시키지 않음
- 거부 사건은 기록할 수 있지만 `consumes_turn=false`여야 함

실행 계층에서도 방어적으로 수치 범위를 확인한다.

### A3. 고정된 처리 단계 문서화

이번 단계의 실제 처리 순서를 코드와 문서에 고정한다.

```text
명령 검증
→ 행동 사건 생성 및 즉시 상태 적용
→ 환경 반응 단계
→ 피해·사망 처리
→ 사건 확정
→ 유효한 행동인 경우에만 턴 증가
```

아직 NPC 스케줄러는 만들지 않는다. 다음 단계에서 아래 순서로 확장할 수 있도록 `Simulator`는 조율만 담당하게 한다.

## B. 원소 시스템 교정

### B1. 물 상태 단순화

현재 `water_depth`와 `wetness`가 모순 상태를 만든다. 이번 단계에서는 연속 유체를 구현하지 않는다.

- `wetness` 하나만 유지하는 것을 우선 권장한다.
- `water_depth`를 유지하려면 깊이·표면 수분·증발·전도성 사이의 불변식을 테스트로 완전히 고정해야 한다. 단순 삭제가 더 안전하다.
- 젖음의 자연 감소 규칙을 작은 정수 상수로 명시한다.
- 젖음이 0이 되면 관련 출처 상태도 정리한다.

### B2. 물–불 반응은 턴당 한 번

현재 물이 즉시 `fire -= water * 2`를 수행한 뒤 같은 step의 `_tick_fire()`에서 다시 억제한다. 이를 제거한다.

권장 구조:

1. `apply_water()`는 젖음 상태와 물 적용 사건만 만든다.
2. 단일 환경 반응 단계가 젖음과 불의 반응을 정확히 한 번 계산한다.
3. 부분 진화에는 정확한 잔여 불 수치와 하나의 결과 사건만 존재한다.
4. 결과 사건은 물 적용 사건까지 인과관계가 이어진다.

억제량, 수분 소비량, 자연 연소 감소량의 규칙을 상수와 테스트로 명시한다. 의미 없이 도달 불가능한 `FIRE_DRYING_PER_TURN` 같은 상수는 제거한다.

### B3. 직접 점화와 확산의 공통 규칙

직접 점화와 화재 확산이 동일한 `try_ignite()` 또는 동등한 공통 규칙을 사용하도록 한다.

- 가연성
- 현재 젖음
- 점화 위력
- 이미 타는 중인지

위 네 조건이 동일하게 해석되어야 한다. 점화 실패가 젖음을 증발시키는 규칙이라면 별도 상태 변화 사건을 기록하고 실패 이유를 구분한다. 의도하지 않았다면 비가연성 타일의 젖음을 변경하지 않는다.

### B4. 2단계 화재 확산

현재 타일 순회 중 이웃 상태를 즉시 바꾸지 않는다.

```text
현재 화재 상태 스냅숏
→ 모든 확산 후보와 RNG 판정 수집
→ 동일 타일 후보를 명시적인 규칙으로 해결
→ 결과를 좌표 순서로 일괄 적용
```

- 두 화원이 같은 타일을 노릴 때 행 우선 순회가 결과를 독점해서는 안 된다.
- 충돌은 높은 유효 화력 우선, 동률이면 고정 좌표 순서처럼 설명 가능한 규칙을 쓴다.
- 새로 붙은 불은 다음 턴부터 다시 확산한다.

### B5. 전기 규칙

- 방전 위력도 `1..100` 검증
- 전도 임계치 24/25 경계 테스트
- 거리마다 정확한 감쇠 테스트
- 분기·순환 경로에서 개체당 한 번만 피해
- 기본 전도성이 높은 금속 타일 경로 테스트
- 각 아크는 최초 방전 사건이 아니라 바로 이전 부모 아크를 `cause_id`로 가리키고 `from_position`을 기록

## C. 사건 인과관계와 출처

### C1. 환경 상태의 출처

타일 또는 작은 효과 상태에 최소한 다음 출처를 보존한다.

```text
fire_source_event_id
wetness_source_event_id
```

필요하다면 최종 책임자를 빠르게 찾기 위한 `instigator_id`를 사건에 추가한다.

- 루트 행동: `actor_id == instigator_id`
- 파생 환경 사건: 즉시 행위자는 환경일 수 있으나 `instigator_id`는 원래 행위자를 계승
- 화재 확산: 직전 점화/확산 사건을 부모로 연결
- 젖음에 의한 진화: 젖음을 만든 사건을 부모로 연결
- 자연 소진: 해당 불의 출처 사건과 연결
- 전기 피해: 아크 → 부모 아크 → 방전 행동으로 역추적 가능

`cause_id != -1`이면 이미 존재하고 현재 사건보다 작은 ID인지 `WorldState`에서 검증한다. 루트 사건만 `-1`을 허용한다. 완전한 이벤트 소싱은 만들지 않는다.

### C2. 피해 시스템 분리

`EnvironmentSystem`이 개체 체력을 직접 변경하지 않도록 작은 `DamageSystem`을 추가한다.

- 모든 피해가 이 시스템을 통해 체력을 변경
- 피해량 정규화
- 피해 사건
- 체력 0 도달 시 사망 사건을 정확히 한 번 생성
- 죽은 개체에 중복 피해·중복 사망 없음
- 불 피해와 전기 피해가 같은 진입점을 사용

## D. 저장·복원과 리플레이 기반

### D1. 스냅숏 완전성

스냅숏에 포함할 것:

- `snapshot_version`
- `ruleset_version`
- 크기, 턴, 시드
- RNG 상태(64비트 손실에 주의)
- 다음 개체 ID
- 다음 사건 ID
- 모든 타일 상태와 환경 출처
- 개체 상태
- 관계 기준표와 개인 관계 상태
- 사건 로그 또는 명시적으로 정한 보존 범위

각 모델에 `from_dict()` 또는 동등한 복원 경로를 만들고 `WorldState.from_snapshot()`을 제공한다.

### D2. 명령 직렬화

`SimCommand.to_dict()/from_dict()`를 구현한다. 저장/리플레이는 완전한 이벤트 소싱 대신 다음 방식을 사용한다.

```text
초기 또는 중간 스냅숏 + 이후 명령 저널 + 턴별 상태 해시
```

중간 저장 후 재개한 최종 상태, RNG, 다음 ID, 사건 순서가 중단 없이 실행한 경우와 동일해야 한다.

## E. 종족 기준선 우선 관계 시스템

### E1. 개체 정체성

`SimEntity`에 데이터 기반 식별자를 추가한다.

```text
species_id: String
faction_id: String   # 이번 단계에서는 빈 문자열 허용
```

`kind`는 표시/역할 용도로 유지할 수 있지만 종족 관계 판단에 사용하지 않는다.

### E2. 방향성을 가진 종족 관계표

`SpeciesRelationTable` 또는 동등한 작은 모델을 만든다. 관계는 방향성이 있어야 한다.

```text
goblin → human
human → goblin
```

두 값이 달라도 된다. 최소 축:

```text
base_trust: -100..100
base_fear: 0..100
base_hostility: 0..100
```

알 수 없는 조합에는 명시적인 중립 기본값을 적용한다. 같은 종족 기본값도 데이터로 설정 가능하게 한다.

### E3. 희소한 개인 관계

실제로 상호작용한 방향 쌍만 개인 관계를 생성한다.

```text
observer_id → subject_id
personal_trust_delta
personal_fear_delta
gratitude
grievance
processed_source_event_ids
```

개인 보정은 정해진 범위로 제한한다. 일반적인 한두 사건만으로 강한 종족 적대 기준선을 뒤집을 수 없어야 한다.

권장 정책:

- 종족 기준값은 최종 관계의 주된 prior다.
- 일반 개인 신뢰 보정은 예를 들어 `-40..40`처럼 제한한다.
- 감사와 원한은 신뢰와 별도 축으로 둔다.
- 한 번 구조받으면 `gratitude`가 의미 있게 증가하지만 `personal_trust_delta`는 작게 증가한다.
- 종족 기준 신뢰가 매우 낮고 적대도가 높으면 한 번의 구조 후에도 최종 disposition은 최소 `WARY` 또는 `HOSTILE`로 남는다.
- 장기적으로 종족 기준선을 넘는 관계는 일반 수치 누적이 아니라 명시적인 `bonded`, 귀화, 세력 화해 같은 별도 상태로만 허용할 수 있다. 이번 단계에서는 그 우회 상태를 구현하지 않아도 된다.

최종 값의 정확한 공식은 코드와 문서에 하나로 고정한다. 예:

```text
effective_trust = clamp(base_trust + bounded_personal_trust_delta, -100, 100)
effective_fear = clamp(base_fear + bounded_personal_fear_delta, 0, 100)
effective_hostility = clamp(base_hostility + grievance_effect - gratitude_relief, 0, 100)
```

단, 감사 한 번이 적대도를 크게 지우지 않도록 계수를 보수적으로 둔다.

### E4. 관계 사건 처리

아직 완전한 인지·기억 시스템은 만들지 않는다. `RelationshipSystem`은 “이 개체가 해당 사건을 관찰했다”는 사실이 외부에서 확인됐다는 전제하에 명시적으로 호출한다.

최소 API 또는 동등한 행위:

- `record_aid(observer_id, helper_id, source_event_id, magnitude)`
- `record_harm(observer_id, attacker_id, source_event_id, magnitude)`
- `effective_relation(observer_id, subject_id)`

같은 `source_event_id`를 두 번 처리해 관계가 중복 변경되지 않도록 한다. 관계 변화 사건도 원인 사건을 가리켜야 한다.

필수 시나리오:

```text
종족 기준: goblin → human
base_trust=-70, base_fear=35, base_hostility=75

인간이 고블린을 한 번 구조
→ gratitude 증가
→ personal_trust_delta 소폭 증가
→ effective_trust는 여전히 음수
→ 최종 태도는 즉시 FRIENDLY/TRUSTING이 되지 않음
```

반복적인 도움은 개인 보정을 누적하지만 일반 상한 안에서만 움직인다. 저장·복원 후에도 동일해야 한다.

## F. 테스트 러너와 필수 회귀 테스트

### F1. 테스트 러너

자체 러너를 유지한다면 다음을 보강한다.

- 테스트 디렉터리와 스크립트 로드 실패 감지
- 테스트 0개 발견 시 실패
- 각 테스트가 명시적인 완료 값을 반환하게 하여 런타임 중단을 성공으로 오인하지 않음
- 실패 시 프로세스 종료 코드 1

외부 테스트 프레임워크 설치는 하지 않는다.

### F2. 필수 테스트

1. 같은 시드·명령열의 동일 상태
2. 거부 명령이 턴·RNG·불 상태를 변경하지 않음
3. `fire=30`, `water=10` 부분 반응이 정확히 한 번만 계산됨
4. 젖음의 정확한 감소와 0 경계
5. 직접 점화와 확산이 동일한 젖음 규칙 사용
6. 두 화원이 같은 타일을 노리는 확산 충돌
7. 좌우/상하 반전 시 순회 편향이 없음
8. 전도 임계치 24/25
9. 거리 감쇠와 순환 경로의 단일 피해
10. 불·전기 피해가 `DamageSystem`을 통함
11. 모든 비루트 사건의 `cause_id`가 존재하며 더 작은 ID
12. 명령 직렬화 왕복
13. 중간 저장·복원 후 연속 실행 동등성
14. 복원 후 개체·사건 ID 중복 없음
15. 고블린→인간의 강한 종족 적대 기준선
16. 인간의 단 한 번 구조가 감사는 만들지만 즉시 신뢰/우호를 만들지 않음
17. 같은 도움 사건의 중복 처리 방지
18. 관계 상태의 스냅숏 왕복

## 실행 및 보고

Godot이 샌드박스 밖 사용자 설정 경로에 쓰지 않도록 필요하면 `/tmp` 아래 XDG 경로를 사용한다.

```bash
XDG_DATA_HOME=/tmp/living-world-sim-data \
XDG_CONFIG_HOME=/tmp/living-world-sim-config \
XDG_CACHE_HOME=/tmp/living-world-sim-cache \
GODOT_SILENCE_ROOT_WARNING=1 \
godot --headless --path /mnt/d/STARTU/living-world-sim \
  --script res://tests/run_tests.gd
```

최종 보고에는 다음을 포함한다.

1. 변경한 파일
2. 실제로 선택한 규칙과 수치 공식
3. 새 테스트 목록
4. 테스트·데모 실행 결과
5. 아직 남은 위험과 다음 단계 진입 조건
