# 성격을 가진 주민의 원정 정착지 — 구현계획

작성일: 2026-09-22
상태: 논의용 초안. 이번 작업은 계획서 작성만 하며 게임 구현·배포는 하지 않는다.

## 1. 목표

플레이어가 도시를 건설하고 타일 단위로 편집할 수 있으며, 주민의 HEXACO·기억·현재 상태가 생활 속 선택으로 드러나는 원정 거점을 만든다. 운영의 중심은 출정 사이의 치료·제작·보급·시설 투자다. 주민을 계속 직접 조종하는 것을 전제로 하지 않는다.

성공 기준은 시설 수가 아니라 “숫자창을 보지 않아도 이 주민의 성격을 행동으로 구별할 수 있는가”다. 건설은 그 주민들이 살고 일하는 공간을 만들고 확장하는 수단이다.

## 2. 합의된 방향과 이번 초안의 제안

대화에서 정한 방향:
- 도시 건설을 지원하고 벽·문·설비 등을 타일 단위로 수정할 수 있다.
- 기본 운영은 원정 사이에 결정을 내리는 거점 방식이다.
- 기존 HEXACO를 주민의 개성과 자율 행동에 활용한다.
- 모바일 조작을 기준으로 한다.

아래 수치·주민 수·시간 규칙은 구현을 구체화하기 위한 제안이며 확정 사양이 아니다.
- 최초 검증: 24×24 정착지, 주민 총 3명(현재 원정 주인공 1명 + 거점 주민 2명).
- 기본 청사진과 수동 타일 편집은 같은 데이터와 배치 검증을 사용한다.
- 기본 시작 공간은 숙소·창고·작업장이고, 첫 확장은 치료 병상이다.
- 소수의 유한 작업을 운영 주기마다 배정한다. 실시간 방치 보상과 오프라인 진행은 제외한다.
- 기존 판타지 메카 컨셉의 인격·기억은 유지하되, 이번 계획으로 용어·아트 전환까지 확정하지 않는다. 기존 컨셉 문서의 2인·방별 원정 설명 대신 현재 1인 연속 층을 연결 기준으로 삼는다.

## 3. 첫 플레이 흐름

1. 정착지에서 주민 상태·미완료 작업·물자를 확인한다.
2. 필요한 경우 청사진을 배치하거나 방을 확장하고 작업대를 설치한다.
3. 주민에게 역할과 우선순위를 정하고 치료·제작 작업을 의뢰한다.
4. 기존 상점에서 원정 물자를 준비하고 주인공이 출정한다.
5. 원정 종료를 정산한 뒤 거점 작업 결과를 한 번 반영한다.
6. 부상을 안고 돌아온 주인공을 보고 남아 있던 주민들이 돌봄·휴식·기존 작업 사이에서 선택한다.
7. 이유가 표시된 짧은 행동 기록을 보고 다음 운영을 결정한다.

대표 장면: 부상자가 귀환했을 때 한 주민은 돌봄을 선택하고 다른 주민은 맡은 제작을 끝낸다. 둘 다 기여할 수 있어야 하며, 특정 성격이 항상 좋은 일꾼이 되는 구조를 피한다.

## 4. 건설과 시설 운영

### 공간 모델

- 바닥, 벽, 문, 가구·설비, 출입·작업 위치를 분리한다.
- 청사진은 이 타일·설비들의 묶음이다. 청사진 건물의 벽도 개별 편집할 수 있다.
- 첫 버전 시설 기능은 설비와 도달 가능성으로 판정한다. 복잡한 방 크기·장식·동선 효율 보정은 제외한다.
- 병상 추가가 치료 슬롯 증가를 뜻한다. 같은 증가를 별도 시설 레벨 구매로 다시 요구하지 않는다.
- 새 제작법은 설비/임무 해금으로 추가할 수 있으나, 공간 확장과 기술 해금은 UI에서 구별한다.

### 편집 계약

- 편집 중에는 시뮬레이션을 멈추고, 미리보기→유효성 검사→비용 확인→확정 순서로 처리한다.
- 확인 전 변경은 무료 취소한다. 확정된 철거의 환급률은 별도 밸런스 항목이며 초기에는 명시된 고정 규칙을 사용한다.
- 주민·출입구·필수 설비를 벽으로 가두거나, 여러 설비가 같은 칸을 차지하는 변경은 거부한다.
- 사용 중인 병상/작업대 철거는 작업 해제와 재배치를 먼저 안내한다. 환자나 예약 자원을 삭제하지 않는다.
- 경로와 시설 캐시는 공간 변경 시에만 무효화한다. 매 프레임 전체 방 검색은 하지 않는다.

### 최초 운영 기능

| 공간/설비 | 기능 | 최초 범위 |
| --- | --- | --- |
| 숙소/침대 | 휴식·스트레스 완화 | 대상과 자리 예약 |
| 창고 | 건설·제작 재료 보관 | 하나의 공용 재고, 운반 미세 조작 제외 |
| 작업장/작업대 | 보급품 제작 | 고정 레시피 1개부터 |
| 치료 병상 | 귀환자 치료 | 체력·스트레스부터, 부위 복구는 별도 단계 |
| 원정문/상점 | 임무·보급·출정 | 현재 원정과 구매/환불 기능 연결 |

부위 손상 복구는 기존 `Body.heal`로 구현됐다고 간주하지 않는다. 혈액·충격 회복과 조직·기능 복구를 구분한 전용 계약과 테스트가 필요하다.

## 5. 주민의 선택과 HEXACO

성격은 선택의 가중치이며 행동 가능 여부를 대신하지 않는다. 먼저 생존·안전, 역할 권한, 예약, 경로, 자원 조건으로 가능한 행동을 추린다. 그 안에서 작업 우선순위 + 현재 욕구 + 기억 + 성격 성향으로 선택한다. 동률은 시드·주민 ID·결정 번호로 재현 가능하게 해소한다.

아래는 게임용 가설이며 실제 사람의 행동을 예측하는 심리 규칙으로 주장하지 않는다.

| 축 | 초기 선택 장면 | 한쪽만 유리해지지 않게 할 조건 |
| --- | --- | --- |
| H | 공용 물자 배분에서 공평/자기 필요 우선 | 낮은 값이 곧 절도·악행을 뜻하지 않음 |
| E | 위험 준비보다 휴식·동료 돌봄을 우선하는 정도 | 위험 회피와 돌봄 모두 상황별 가치 부여 |
| X | 공동 휴식/대화와 혼자 쉬기 중 선호 | 두 방식 모두 회복 가능 |
| A | 작업 충돌 시 양보·중재와 자기 작업 유지 | 양보가 무조건 생산 손실이 되지 않음 |
| C | 진행 중 작업 마무리와 새 요청 전환 | 낮은 값에 무작위 작업 실패를 부과하지 않음 |
| O | 익숙한 제작과 새 제작법 시험 중 선호 | 실험에는 다른 비용·성과, 단순 상위 선택 금지 |

최초 실행 검증은 A·C의 돌봄/작업 선택과 E의 기존 스트레스 연결에 집중한다. H·X·O를 포함한 나머지 장면은 두 번째 단계에서 추가한다. 모든 축을 첫 버전에 억지로 숫자 보정으로 넣지 않는다.

- 현재 작업을 선택할 때 일정 기간 유지하고, 긴급 상황에서만 중단해 작업 왕복 진동을 막는다.
- 도움받음 등 기존 기억 종류를 먼저 사용한다. 새로운 기억은 enum·직렬화·표시·검증을 함께 확장한다.
- 기억은 현재 최대 8개이며, 사건 ID 중복 방지 규칙을 지킨다. 정착지와 원정이 같은 ID를 발급하지 않게 공용 사건 번호를 둔다.
- “치료가 급한 아린을 돕기로 했다 · 동료 돌봄 선호”처럼 관측된 사실과 실제 선택 요인을 표시한다. 발생하지 않은 행동이나 동기를 꾸며 로그로 쓰지 않는다.
- 플레이어는 역할·우선순위·일회성 작업 지정을 할 수 있다. 성격 때문에 지시를 예고 없이 무효화하지 않는다.

## 6. 시간과 원정의 연결

초기 제안은 명시적인 운영 주기다. 한 주기를 일정 수의 결정 스텝으로 구성하고, 이동·작업을 같은 스텝으로 처리한다. 화면 애니메이션은 그 결과를 재생하며 별도로 생산하지 않는다.

- 건설·메뉴·앱 백그라운드에서는 주기가 진행되지 않는다.
- 출정 시 정착지에 남은 주민과 예약 작업을 기록한다. 출정자는 정착지 작업을 수행할 수 없다.
- 원정 종료 시 해당 출정에서 실제 소비한 행동에 비례한 작업량을 상한 내에서 정산한다. 즉시 포기·입구 왕복은 한 주기 전체 보상을 만들지 않는다.
- 원정 없이 진행하려면 ‘정착지에서 하루 보내기’라는 명시적인 선택으로 한 주기를 진행한다. 작업 비용과 대기 결과를 먼저 보여준다.
- 무한 제작·무한 자원 채집은 첫 범위에서 제외한다. 재료가 없으면 진행이 멈춘다.
- 작업량 환산과 상한은 수치 검증으로 확정한다. 원정의 표시 라운드 대신 실제 행동 누계/종료 사건을 연결 기준으로 삼는다.
- 정착지 진행은 원정 패배 스냅샷의 복원 대상이 아니다. 출정 전 확정된 건설·거래·거점 작업을 패배로 되돌리지 않는다.
- 성공·중도 귀환·패배·포기 모두 출정 ID로 한 번만 정산한다. 결과창 재열기와 저장 복원으로 작업을 중복 완료하지 않는다.

## 7. 상태와 모듈 설계

`Session`에 정착지 로직 전체를 추가하지 않고, 별도 상태와 얇은 연결 계층을 둔다. 원정 주인공의 영구 상태와 주민 목록은 공용 캠페인 상태를 참조하고 원정은 출정자만 선택한다.

| 제안 파일 | 책임 |
| --- | --- |
| `settlement/state.gd` | 스키마 버전, 맵, 주민 ID, 재고, 작업, 사건/운영 번호 |
| `settlement/building_rules.gd` | 청사진·타일 편집·접근성·비용·작업 위치 검증 |
| `settlement/job_rules.gd` | 생성→예약→진행→완료/취소, 중복 소비/지급 방지 |
| `settlement/resident_choice.gd` | 가능 행동 필터, 성격·기억·욕구 평가, 이유 반환 |
| `settlement/simulation.gd` | 결정 스텝 실행, 작업/위치 반영, 반복 진행 제한 |
| `settlement/expedition_bridge.gd` | 출정자 분리, 종료 사건 반영, 재고와 상점 연결 |
| `settlement/view.gd` | 지도·주민·배치 미리보기, 판정/경제 상태 직접 수정 금지 |
| `settlement/panel.gd` | 시설 운영, 주민 역할, 작업 결과와 이유 표시 |

작업에는 고유 ID, 종류, 대상/설비, 담당자, 예약 재료, 진행량, 완료 결과, 정산 여부를 둔다. 재료는 시작 시 예약하고 완료 시 소비한다. 취소 시 미소비 예약분만 반환한다. 화면 버튼은 명령만 보내며 잔액이나 작업 완료를 직접 바꾸지 않는다.

지속 플레이용 구현에는 버전 있는 저장/복원과 원자적 파일 교체가 필요하다. 최초 행동 검증은 메모리 상태로 가능하지만, 사용자 플레이 단계 진입 전 저장/복원 검증을 완료한다. 모바일 앱 종료로 도시를 잃는 상태를 완성본으로 간주하지 않는다.

## 8. 재사용 조사

현재 코드 확인 결과:
- `sim/dungeon_population/hexaco_profile.gd`: 6축 0~1000, 결정론적 생성과 직렬화를 그대로 재사용한다.
- `sim/party_memory_state.gd`: 기존 기억, 중요도 유지, 사건 중복 방지를 재사용한다.
- `expedition/session.gd`: 출정·정산·상점·스냅샷 경계를 연결 지점으로 삼는다. 원정 공급품과 정착지 재고의 소유권은 이중 관리하지 않는다.
- `expedition/character_ui.gd`: 성격·기억 화면을 주민 상세에서 재사용할 수 있다.
- 부모 프로젝트 `../sim/base_settlement_rules.gd`: 16×16 건물 footprint·배치 규칙이 있지만 내부 타일 편집을 바로 제공하지는 않는다.
- `../sim/settlement_work_rules.gd`: 채집·운반·건설·생산의 작업/예약과 증분 캐시 구조를 검토할 수 있다. `world.events`와 기존 경제 규칙 의존성이 있어 통째 이식하지 않는다.
- `../playtest/town_resident_motion.gd`: 월드 상태를 바꾸지 않는 장식용 이동이다. 작업·성격 AI로 오인해서 사용하지 않는다.

구현 시작 시 부모 코드의 필요한 함수와 테스트 의존성을 추가 조사한다. 현재 폴더 밖의 런타임 경로를 직접 참조하지 않고, 필요한 코드를 가져올 때 출처·변경점을 기록한다.

## 9. 모바일 인터페이스

- 기본 화면은 정착지 지도, 상단 자원/운영 상태, 하단 건설·주민·작업·원정으로 구성한다.
- 건물을 누르면 운영 패널, 주민을 누르면 현재 행동·이유와 상세 상태를 연다.
- 청사진 배치는 끌기/회전/확정으로, 세밀 편집은 별도 모드에서 벽·문·바닥·가구 도구로 한다.
- 핀치 확대와 지도 이동은 배치 확정/철거로 해석하지 않는다.
- 편집 중 비용·접근 불가 이유를 미리 표시하고 일괄 취소를 제공한다.
- 작은 캐릭터를 계속 누르지 않아도 주민 목록으로 작업을 지정할 수 있다.
- 390×844, 412×915에서 주요 터치 영역 44px 이상, 패널 스크롤과 안전한 닫기를 확인한다.

## 10. 단계와 완료 조건

| 단계 | 구현 범위 | 완료 조건 |
| --- | --- | --- |
| 0. 계약 | 공용 주민 ID·사건 번호·경제 소유권·시간·저장 형식 | 원정과 중복 정산/복원 충돌이 없는 상태 전이 예시 |
| 1. 성격 검증 | 고정 공간, 주민 3명, 돌봄/작업/휴식 | 같은 상황에서 성격에 따라 선택 차이가 재현되고 이유가 설명됨 |
| 2. 건설 | 청사진 1종, 벽·문·병상 편집 | 방 확장과 병상 추가가 실제 서비스 슬롯을 바꿈 |
| 3. 거점 운영 | 공용 재고, 제작 1종, 역할·예약·취소 | 이중 소비·중복 완료·설비 철거 고립 없음 |
| 4. 원정 연결 | 실제 출정/귀환/패배/포기, 상점 연결 | 원정 3회와 거점 운영이 동일 주민·재고로 이어짐 |
| 5. 플레이 검증 | 저장/복원, 모바일 UI, 로그·속도 조절 | 재실행 후 상태 일치, 조작 가능, 주민 차이를 알아볼 수 있음 |

단계 1의 고정 공간은 검증용이며 최종 제품을 고정 시설 메뉴로 바꾸는 결정이 아니다. 타일 기반 상태는 단계 0부터 사용해 단계 2에서 다른 건설 시스템을 붙이지 않는다.

## 11. 검증과 판단 기준

자동 검증:
- 동일 시드·상태·명령열의 결정과 정산이 동일하다. 성격 한 축만 바꾼 비교에서 설계한 선택 차이가 나타난다.
- 응급 상황과 접근 불가 조건이 성격 선호보다 우선한다. 특정 성격 때문에 필수 치료·작업이 영구 중단되지 않는다.
- 주민·병상·작업대·재료 중복 예약, 음수 재고, 중복 지급이 없다.
- 편집 취소·철거·막힌 문·출정자 부재·패배 복원·동일 종료 사건 재수신을 검사한다.
- 즉시 포기 반복, 무료 보급 반복, 환불, 제작 취소로 재료나 자금이 복제되지 않는다.
- 저장 왕복 후 위치·주민·기억·재고·작업 진행·정산 기록이 일치한다.
- 기존 솔로 원정·횃불·상점·동료·보스 테스트를 유지한다.

실제 플레이 검증:
- 성격 수치를 숨긴 상태에서 세 주민의 행동 차이를 설명할 수 있는가?
- 치료 병상을 늘린 공간 편집이 의미 있는 운영 변화로 느껴지는가?
- 다음 원정 목표가 도시의 필요에서 한 번 이상 생기는가?
- 주민별 반복 지시 없이 한 운영 주기를 마칠 수 있는가?

판단: 성격 차이가 안 보이면 행동 선택/피드백을 먼저 수정하고 시설을 늘리지 않는다. 타일 편집이 번거로우면 청사진·확장 도구를 개선한다. 차이를 만들기 위해 벌점·갈등만 늘리지 않는다.

## 12. 첫 범위에서 제외

대규모 주민, 습격·정착지 전투, 전력·배관·온도·농업, 연애·가계도, 실시간 동시 원정, 무제한 오프라인 생산, 영구 사망/인격 복구, 세계관 전체 개명은 후속 범위다. 최종 도시 규모와 모든 HEXACO 축의 생활 장면은 초기 검증 뒤 정한다.
